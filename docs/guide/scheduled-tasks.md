# 定时任务

[English](scheduled-tasks.en.md)

定时任务保存在设备上，由该设备的 agent 按计划在后台执行非交互命令，例如定期运行脚本或 AI CLI。本文面向拥有者，说明如何在网页和设备本机的 `kiteline-agent schedule` 中管理同一份任务。

## 创建与编辑

在“定时任务”中创建任务，保存后不能更改所属设备。设备离线时，列表只有 server 保存的最近摘要，不能编辑或运行任务。

常用周期按调度时区换算成 Cron 表达式，见[计划规则](#计划规则)。预览的下次执行时间按浏览器所在时区显示，可能与调度时区不同。

工作目录必须是设备上已存在的目录，在新建或修改它时检查。目录之后被删除或移走，该次运行失败，原因显示“命令无法启动”。

### 编辑与删除

保存只提交改过的字段。正在执行的运行继续使用开始时的命令和工作目录，修改从下一次运行起生效。

打开表单后，任务若被其他入口修改过，保存会失败并保留输入。读取当前定义，核对后再次保存。连接中断导致保存结果不明时，按表单给出的任务 ID 查询结果，不要重复提交。

点“删除”并确认后，任务定义和它保留的运行记录一起删除，命令写出的文件保留。任务有运行未结束时不能删除，先停止该运行。

## 计划规则

### Cron 表达式

使用五个数字字段：分、时、日、月、星期。每个字段可以是 `*`、数字、列表（`1,15`）、范围（`1-5`）或步长（`*/10`）。星期用 0 至 6 表示，0 是星期日。英文名称（如 `MON`）、秒字段和 `@daily` 之类的写法不被接受。表达式长度有上限（见[限额](reference.md#限额)），并且必须至少有一次未来的执行时间。

同时限定“日”和“星期”时，两者满足其一即执行。例如 `0 9 13 * 5` 在每月 13 日和每个星期五的 09:00 执行。

### 单次计划

网页的“日期与时间（浏览器本地）”按浏览器所在时区输入。命令行的 `--at` 使用带秒的 ISO 8601 时间，并带 `Z` 或 `+08:00` 这样的偏移，例如 `2027-01-05T09:00:00+08:00`；`2027-01-05T09:00+08:00` 会被拒绝。时间必须在未来。

单次计划最多执行一次，状态依次显示为“待执行”“计划已消耗”或“已错过”。计划时刻因“上次运行仍未结束”或“设备运行数量已达上限”被跳过时，单次计划同样变为“计划已消耗”，命令没有执行，之后也不会再执行；需要时修改计划时间重新安排。“立即运行”不消耗单次计划。修改计划时间会生成新的单次计划，状态回到“待执行”。

### 调度时区

Cron 表达式按任务的调度时区解释，时区写 IANA 名称，例如 `Asia/Shanghai`；`+08:00` 这样的固定偏移会被拒绝。不指定时使用保存时设备的时区，并随任务保存，之后不随浏览器或设备时区变化。调度时区只决定何时执行，命令运行时的 `TZ` 环境变量仍来自 agent。

夏令时切换时，不存在的本地时间被跳过，重复出现的本地时间只执行一次。

### 错过的执行

计划时刻到来时 agent 没有运行或任务处于暂停，这次执行被跳过，之后也不补跑。agent 启动或任务恢复后，从当前时间计算下一次执行。

agent 在运行但计时器晚于计划时刻且超过迟到容差（见[限额](reference.md#限额)，例如系统刚从休眠中恢复），这次执行记为“已跳过”，原因是“已错过计划时间”。单次计划的时间在 agent 停止或任务暂停期间过去时，这次计划不会执行；agent 下次启动或任务被恢复、修改时，状态变为“已错过”，并留下一条“已跳过”记录。

## 执行环境

命令由 agent 配置的 Shell 以非交互方式执行（Linux、macOS 为 `SHELL -c COMMAND`，Windows 为 PowerShell 的 `-Command`），Shell 的默认值和完整参数见 [shell](reference.md#shell)。

- Shell 既不是登录 Shell，也不是交互 Shell。命令依赖的设置若来自 `~/.bashrc`、`~/.profile` 或 PowerShell profile，请把它们写进命令，或放进 agent 的启动环境。
- Windows 任务的文本输出使用 UTF-8；外部程序的输出编码也应设为 UTF-8。
- Windows PowerShell 5.1 默认以 ASCII 把字符串送入原生程序的 stdin；需要中文输入时，在命令中显式设置 `$OutputEncoding = [Text.UTF8Encoding]::new($false)`。文件重定向仍使用所选 Shell 的默认编码。
- 标准输入已关闭，也没有终端（PTY）。需要终端或等待人工确认的程序会失败或立即读到输入结束，AI CLI 需要使用它的非交互方式运行。
- 命令以 agent 的操作系统用户运行，继承 agent 进程的环境，包括 `HOME`、`PATH`、代理变量、SSH agent 和 Git 凭据。它不继承执行 `kiteline-agent schedule` 的那个 Shell 的环境和当前目录。agent 作为后台服务运行时，环境由服务配置提供，见[后台运行](devices.md#后台运行)。
- 默认工作目录是项目用户的 HOME（Windows 上是用户配置文件目录）。
- 没有默认的运行时长上限，命令一直运行到退出或被停止。输出超过限额也不会结束命令。
- 命令在独立的进程组（Linux、macOS）或 Job（Windows）中运行，停止时作用于其中所有进程。命令应在前台完成工作；在 Linux 和 macOS 上，自行脱离进程组的后台进程不受停止操作管理。
- 定时任务不进入 tmux，不能附着，结果通过运行记录查看。

退出码为 0 时运行结果为“成功”；非 0 时为“失败”，原因“命令未成功退出”；工作目录或 Shell 不可用导致无法启动时为“失败”，原因“命令无法启动”。

## 运行与停止

- **立即运行。** 关闭浏览器或命令行不会停止运行。
- **并发。** 同一任务同时只有一次运行，每台设备同时运行的数量有上限（见[限额](reference.md#限额)）。条件不满足时，“立即运行”报“资源正忙。”；定时执行不排队，直接记为“已跳过”，原因是“上次运行仍未结束”或“设备运行数量已达上限”。
- **暂停与恢复。** “暂停计划”停止之后的定时执行，正在执行的运行不受影响，暂停期间仍可“立即运行”。“恢复计划”从当前时间重新计算下一次执行。
- **停止。** 停止运行不回滚命令已经完成的改动。Linux 和 macOS 向整个进程组发送 `SIGTERM`，等待停止宽限（见[限额](reference.md#限额)）后仍未结束则发送 `SIGKILL`；Windows 立即结束整个 Job。
- **agent 正常停止。** 用 Ctrl-C、服务管理器或升级前停止 agent 时，正在执行的运行按同样方式停止，记为“已停止”，原因是“Agent 已停止”。任务定义和记录保留，agent 再次启动后继续按计划执行。
- **不自动重试。** 失败或跳过的执行不会重试，下一次计划照常执行。

“立即运行”的结果不明时，先按页面给出的运行 ID 查询是否已经开始，再决定是否重新运行。

## 运行记录与输出

stdout 和 stderr 分开保存，两者之间没有统一的时间顺序。

输出和记录有保留上限，数值见[限额](reference.md#限额)：

- 每次运行的 stdout 和 stderr 合计有上限。超出部分不保存，命令继续运行。
- 每个任务只保留最近 `taskHistoryRuns` 条已结束的记录，“已跳过”的记录也计入。
- 设备上的输出总量有上限。开始新运行时，agent 可能从最早的已结束记录起删除带输出的记录。正在执行和待核查的运行不会被删除；剩余空间不足时，新运行的输出可能更早被截断。

记录保存在 agent 数据目录的 `tasks/` 中（见[文件位置](reference.md#文件位置)），agent 重启和升级后仍在，`uninstall --purge-state` 会删除它们。记录不存在不能证明命令从未执行，再次运行前应核查此前的执行情况。命令自己写出的文件留在原处。

## agent 重启后的核查

agent 异常结束（进程被杀、崩溃、断电）时，正在执行的运行没有可信的最终结果。agent 下次启动时：

1. 把这些运行标为“未知”，原因是“上次运行结果未确认”；
2. 暂停对应任务并标记待核查；
3. 在核查完成前拒绝该任务的定时执行和“立即运行”，这次运行继续占用设备的运行名额。

核查步骤：

1. 打开提示中的运行 ID，在“命令与执行环境”中查看命令和 PID。Linux 和 macOS 上命令在独立进程组中运行，agent 结束后它可能仍在运行；按 PID 和命令确认它是否还在，需要时自行结束它。Windows 上命令所在的 Job 随 agent 结束，进程一并结束。
2. 检查命令已经产生的影响，例如写了一半的文件。
3. 确认旧程序已结束后，执行“确认核查”。任务仍保持暂停，记录仍为“未知”。
4. 需要继续按计划执行时，点“恢复计划”。

待核查的任务也可以直接删除，删除确认中包含同样的核查确认。

agent 启动时无法读取 `tasks/` 中的文件时，该设备的任务功能显示“此设备的任务存储不可用。”，agent 日志以 `Scheduled task storage:` 开头写出出错的文件。终端、文件和 Git 不受影响。修复或移走出错的文件后重启 agent。agent 不会自动修复或删除这些文件。

## 命令行

`kiteline-agent schedule` 在设备本机管理同一份任务。管理任务需要 agent 已运行；命令必须由运行 agent 的同一操作系统用户执行，并解析到相同的运行目录。命令不会启动 agent。

完整子命令、参数和输出格式见现有英文帮助；查看帮助不需要配置或运行 agent：

```sh
kiteline-agent schedule --help
kiteline-agent schedule update --help
```

例如，先预览计划、创建任务，再运行并查看状态和输出。把 `TASK_ID`、`RUN_ID` 换成前一步结果中的 ID：

```sh
kiteline-agent schedule preview --cron '0 9 * * 1-5' --timezone Asia/Shanghai --json
kiteline-agent schedule create --name 'Daily review' --cron '0 9 * * 1-5' --timezone Asia/Shanghai --cwd '/srv/My Project' --command './daily-review.sh' --json
kiteline-agent schedule run TASK_ID --json
kiteline-agent schedule status RUN_ID --json
kiteline-agent schedule output RUN_ID --stream stdout --offset 0 --json
```

任务和运行 ID 在各自记录的生命周期内不变；保留结果中的 ID，用于查询、停止和核查。退出码为 3 表示结果未确认，应按输出中的 `taskId` 或 `runId` 查询，不要直接重发同一操作。

Windows 上的调用方式见 [kiteline-agent 命令](reference.md#kiteline-agent-命令)。在 PowerShell 中读取 JSON 列表：

```powershell
& (Join-Path $PSHOME $(if ($PSVersionTable.PSVersion.Major -eq 5) { 'powershell.exe' } else { 'pwsh.exe' })) -NoProfile -ExecutionPolicy Bypass -File "$env:ProgramData\kiteline-agent\kiteline-agent.ps1" schedule list --json | ConvertFrom-Json
```

### 让 AI CLI 管理任务

把定时任务页提供的提示词模板和你的需求交给设备终端中的 AI CLI，让它先阅读 `kiteline-agent schedule --help`，再用命令行创建和管理任务。
